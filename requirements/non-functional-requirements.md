# 非機能要件定義書

本書は「何を満たすべきか」という要求のみを記述する。環境ごとの具体的なパラメータ（Auto Scalingの閾値、CPU/メモリ、ログ保持日数、DBインスタンスクラス等）は[環境定義書](../environment-definitions/)に、なぜその設計・運用方針を選んだかは各ADR（`tomario-steering/adr/infra/`）に記載する。カテゴリはIPA非機能要求グレード×AWS Well-Architectedの7カテゴリ（分類の定義は`tomario-workspace/.claude/reference/nfr-taxonomy.md`）に準ずる。

要求は「必須」「目標」「除外」の3段で揃える。

---

## 1. 可用性

**必須**
- システムは、ECSタスクが異常終了した場合に自動的に再起動し、サービスを継続する。
- システムは、ALBのヘルスチェックにより異常なタスクへのルーティングを自動的に停止する。
- システムは、トラフィック増加時に自動的にスケールアウトする。
- システムは、定期的な自動バックアップを実施し、障害発生時にポイントインタイム復旧を可能とする。

**目標**
- 復旧時点（RPO）は15分以内、復旧時間（RTO）は30分以内を目標とする。

**除外**
- 常時稼働を前提とした可用性SLAは定めない（非公開のポートフォリオ用途のため）。
- AZ障害に対する自動フェイルオーバー（Multi-AZ）は要件としない（判断の根拠は[ADR](../../tomario-steering/adr/infra/database/003-multi-az-cost-tradeoff.md)参照）。

## 2. 性能・拡張性

**必須**
- システムは、負荷増加時にECSタスク数を自動的に増減できる。

**目標**
- 通常時のAPI応答時間は1秒以内を目標とする。

**除外**
- インスタンス・タスクサイズの垂直スケールは要件としない（水平スケールのみで対応する）。

## 3. 運用・保守性

**必須**
- システムのすべてのインフラリソースはコードで管理し（IaC）、手動操作による構成変更を禁止する。
- システムは、インフラ・アプリケーション双方のデプロイをCI/CDで自動化する。
- システムは、デプロイに失敗した場合、自動的に直前の正常な状態へロールバックできる。
- システムは、障害調査のためにアプリケーションログ・インフラログを一定期間保持する。
- システムは、環境（dev/staging/production）ごとにリソースを分離し、環境名を含む命名規則でどの環境のリソースかを即座に識別できるようにする。

**除外**
- 稼働コストを抑えるための起動・停止運用（いつ・どう起動するか）は要件とせず、運用方針として別途定める（[ADR](../../tomario-steering/adr/infra/cost/001-cost-stop-start-operation.md)参照）。

## 4. セキュリティ

**必須**
- システムは、RDS・ECSタスクをプライベートサブネットに配置し、インターネットからの直接アクセスを遮断する。
- システムは、認証情報（DB接続情報・セッション署名鍵）をソースコードに含めず、シークレット管理サービスで管理する。
- システムは、セッション署名鍵を定期的に自動で更新する。更新によってログイン中のセッションが切れないようにする。
- システムは、CI/CDからAWSへの認証に長期アクセスキーを使用しない。
- システムは、保存データおよび転送データを暗号化する。
- システムは、一般公開する環境において、既知のWebアプリケーション層の攻撃を検知・防御する。
- システムは、AWSアカウントへの脅威を継続的に検出する。
- システムは、各IAMロールに必要最低限のアクセスのみを許可する（最小権限）。
- システムは、依存パッケージ・コンテナイメージの既知の脆弱性を継続的に検知し、修正可能な重大な脆弱性（Critical/High）を含むイメージをデプロイしない。

**除外**
- 非公開の検証環境（dev/staging）における常時のWebアプリケーション層防御は要件としない。
- 一般公開前のproduction環境における、常時のWebアプリケーション層防御・コンプライアンス監視（設定の準拠状況の評価）の有効化は要件としない（検証が必要な期間のみ有効化すればよい。判断の根拠は[ADR](../../tomario-steering/adr/infra/security/001-security-stack-cost-management.md)参照）。AWSアカウントへの脅威検出は、上記「必須」のとおり常時行う。

## 5. 移行性

本システムは新規構築のため移行性は対象外とする。既存システムからのデータ移行・並行稼動・切り戻し手順の定義は不要。

## 6. 環境・エコロジー

**必須**
- システムは、対象ユーザー（日本国内）に対して低レイテンシとなるリージョンを使用する。
- システムは、プライベートサブネットからAWSサービスへの通信経路において、インターネットを経由しない設計とする。
- システムは、必要以上のリソースを確保しない。

**使用ソフトウェアのライセンス（制約条件）**

| ソフトウェア | ライセンス |
|------------|-----------|
| Python | PSF License（商用利用可・無償） |
| Flask | BSD-3-Clause（商用利用可・無償） |
| MySQL（RDS） | GPL / 商用（AWSマネージドのため個別ライセンス不要） |
| Terraform | BSL 1.1（商用製品への組み込み以外は無償） |

## 7. コスト最適化

**必須**
- システムは、未使用時に主要リソースを停止・削除できる。
- システムは、予算超過・異常課金を早期に検知する。

**除外**
- 具体的にいつ・どのリソースを・どのインスタンスクラスで起動するかは要件とせず、運用方針・設計判断として別途定める（[ADR一覧](../../tomario-steering/adr/infra/)参照：cost-stop/start運用、DBインスタンスクラス選定、セキュリティスタックの有効化タイミング）。
