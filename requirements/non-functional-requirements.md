# 非機能要件定義書

本書は「何を満たすべきか」という要求のみを記述する。環境ごとの具体的なパラメータ（Auto Scalingの閾値、CPU/メモリ、ログ保持日数、DBインスタンスクラス等）は[環境定義書](../environment-definitions/)に、なぜその設計・運用方針を選んだかは各ADR（`tomario-steering/adr/infra/`）に記載する。カテゴリはIPA非機能要求グレード×AWS Well-Architectedの7カテゴリに準ずる。

要求は「必須」「目標」「除外」の3段で揃える。

本書は、実務と同じく本番運用（一般公開・常時稼働）を前提に記述している。ポートフォリオとして維持するために実際の運用が本書と異なる点は、[ポートフォリオとしての運用上の制約](../portfolio-constraints.md)に記載する。

---

## 1. 可用性

**必須**
- アプリケーションが異常終了した場合も、人手を介さずに自動で復旧し、サービスを継続する。
- 定期的な自動バックアップを実施し、障害発生時にポイントインタイム復旧を可能とする。

**目標**
- 月間稼働率は99.5%を目標とする。
- 復旧時点（RPO）は15分以内、復旧時間（RTO）は30分以内を目標とする。

**除外**
- データセンター単位の障害に対する自動切替えは要件としない（判断の根拠は[ADR](../../tomario-steering/adr/infra/database/003-multi-az-cost-tradeoff.md)参照）。

## 2. 性能・拡張性

**必須**
- 負荷の増減に応じて、処理能力を自動で増減できる。

**目標**
- 通常時のAPI応答時間は1秒以内を目標とする。

## 3. 運用・保守性

**必須**
- すべてのインフラリソースはコードで管理し（IaC）、手動操作による構成変更を禁止する。
- インフラ・アプリケーション双方のデプロイをCI/CDで自動化する。
- デプロイに失敗した場合、自動的に直前の正常な状態へロールバックできる。
- 障害調査のためにアプリケーションログ・インフラログを一定期間保持する。
- 環境（dev/staging/production）ごとにリソースを分離し、環境名を含む命名規則でどの環境のリソースかを即座に識別できるようにする。

**除外**
- 検証環境（dev/staging）の稼働コストを抑えるための起動・停止運用（いつ・どう起動するか）は要件とせず、運用方針として別途定める（[ADR](../../tomario-steering/adr/infra/cost/001-cost-stop-start-operation.md)参照）。

## 4. セキュリティ

**必須**
- データベース・アプリケーションサーバーは、インターネットから直接アクセスできない場所に配置する。
- 認証情報（DB接続情報・セッション署名鍵）をソースコードに含めず、シークレット管理サービスで管理する。
- セッション署名鍵を定期的に自動で更新する。更新によってログイン中のセッションが切れないようにする。
- CI/CDからAWSへの認証に長期アクセスキーを使用しない。
- 保存データおよび転送データを暗号化する。
- 既知のWebアプリケーション層の攻撃を検知・防御する。
- AWSアカウントへの脅威を継続的に検出する。
- システムの各構成要素・運用者には、必要最低限の権限のみを付与する（最小権限）。
- AWSリソースの設定がセキュリティ基準に準拠しているかを継続的に評価する。
- 依存パッケージ・コンテナイメージの既知の脆弱性をイメージのビルド時に検知し、修正可能な重大な脆弱性（Critical/High）を含むイメージをデプロイしない。

**除外**
- 稼働中のイメージに対する定期的な脆弱性の再スキャンは要件としない（デプロイのたびにビルド時のスキャンを行う）。
- CDN→ロードバランサー間の通信の暗号化、および利用者との通信のTLS1.2以上への限定は要件としない（独自ドメイン・証明書を導入しないため。判断の根拠は[ADR](../../tomario-steering/adr/infra/frontend/001-no-custom-domain.md)参照）。
- ロードバランサー→アプリケーションサーバー間の通信の暗号化は要件としない（外部から隔離されたネットワーク内の通信であり、アプリケーションサーバーはロードバランサーからの通信のみを受け付けるため）。

## 5. 移行性

本システムは新規構築のため移行性は対象外とする。既存システムからのデータ移行・並行稼動・切り戻し手順の定義は不要。

## 6. 環境・エコロジー

**必須**
- 対象ユーザー（日本国内）に対して低レイテンシとなるリージョンを使用する。
- 必要以上のリソースを確保しない。

**使用ソフトウェアのライセンス（制約条件）**

| ソフトウェア | ライセンス |
|------------|-----------|
| Python | PSF License（商用利用可・無償） |
| Flask | BSD-3-Clause（商用利用可・無償） |
| MySQL（RDS） | GPL / 商用（AWSマネージドのため個別ライセンス不要） |
| Terraform | BSL 1.1（商用製品への組み込み以外は無償） |

## 7. コスト最適化

**必須**
- 検証環境（dev/staging）の未使用時に主要リソースを停止・削除できる。
- 予算超過・異常課金を早期に検知する。

**除外**
- 具体的にいつ・どのリソースを・どのインスタンスクラスで起動するかは要件とせず、運用方針・設計判断として別途定める（[ADR一覧](../../tomario-steering/adr/infra/)参照：cost-stop/start運用、DBインスタンスクラス選定）。
