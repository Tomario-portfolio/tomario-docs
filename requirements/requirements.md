# 要件定義書

## 1. プロジェクト概要

| 項目 | 内容 |
|------|------|
| プロジェクト名 | Tomario（ホテル予約システム） |
| 目的 | ホテルの客室予約をオンラインで受け付け、空き状況の確認から予約完了までをWebで完結させる |
| 対象ユーザー | ホテルの宿泊予約をしたい一般ユーザー |
| 開発目的 | AWSインフラエンジニアへの転職を目的としたポートフォリオ。インフラ構成の再現性・運用性の証明を主目的とする |

---

## 2. 機能要件

### 2.1 認証機能

- ユーザー登録ができる（ユーザー名・メールアドレス・パスワード）
- ログイン・ログアウトができる
- ログイン状態を維持できる（セッション管理）
  - セッション有効期限：ブラウザを閉じると失効（Flaskデフォルト動作。ポートフォリオ用途のため永続化は未実装）

### 2.2 客室機能

- 客室一覧を確認できる
- チェックイン日・チェックアウト日を指定して空き室を絞り込める
- 客室の詳細（部屋番号・タイプ・定員・料金・説明・画像）を確認できる

### 2.3 予約機能

- ログイン済みユーザーが客室を予約できる
- 自分の予約一覧を確認できる
- 予約をキャンセルできる（以下のキャンセルポリシーに従う）

**キャンセルポリシー**

| チェックインまでの日数 | キャンセル料 |
|---|---|
| 3日以上前 | 無料 |
| 2日前 | 宿泊料金の30% |
| 前日 | 宿泊料金の50% |
| 当日以降 | キャンセル不可 |

※ キャンセル料計算ロジックは今後実装予定
- 同一期間の二重予約を防止する

### 2.4 初期データ（シードデータ）

管理者機能が未実装のため、ECSタスク起動時に客室データを自動投入する。

| 部屋番号 | タイプ | 料金 | 定員 |
|---------|--------|------|------|
| 101 | シングル | 8,000円/泊 | 1名 |
| 102 | シングル | 8,000円/泊 | 1名 |
| 201 | ダブル | 12,000円/泊 | 2名 |
| 202 | ダブル | 12,000円/泊 | 2名 |
| 301 | スイート | 25,000円/泊 | 3名 |

roomsテーブルが空の場合のみ投入される（重複投入なし）。

### 2.5 管理者向け機能

- 予約一覧の確認・客室登録（将来対応予定）

## 3. システム構成

### 3.1 アーキテクチャ概要

```
インターネット
    │
  CloudFront（S3・ALBへのオリジン振り分け）
    ├── S3（フロントエンド静的ファイル）
    └── ALB（パブリックサブネット）
            │
        ECS Fargate（プライベートサブネット）
            │
        RDS MySQL（プライベートサブネット）
```

### 3.2 使用技術・サービス

| レイヤー | 技術・サービス | 選定理由 |
|----------|--------------|---------|
| フロントエンド | HTML / CSS / JavaScript | シンプルなSPAで実装。インフラ検証を主目的とするため最小構成 |
| バックエンド | Python / Flask | 軽量フレームワーク。REST APIの構築が容易 |
| コンテナ | ECS Fargate | 当初EC2で構築したが以下の理由でECS Fargateに移行。①OSパッチ・セキュリティ更新などのサーバー管理が不要になる ②SSHポートを開ける必要がなく攻撃面を削減できる ③ECRへのイメージpushだけでデプロイが完結しCI/CDとの親和性が高い ④コンテナ化により環境差異をなくし再現性が向上する |
| コンテナレジストリ | ECR | ECSとの親和性が高い。IMMUTABLEタグでイメージの不変性を担保 |
| データベース | RDS MySQL 8.0 | マネージドDBでバックアップ・パッチ管理を自動化 |
| ストレージ | S3 | フロントエンド静的ファイルの配信 |
| CDN | CloudFront | S3・ALBへのリクエストを一元管理。HTTPS終端 |
| ロードバランサー | ALB | ECSタスクへのルーティング。ヘルスチェック |
| インフラ | Terraform + AWS | IaCによる再現性・バージョン管理 |
| CI/CD（インフラ） | GitHub Actions + OIDC | terraform plan/applyの自動化 |
| CI/CD（アプリ） | GitHub Actions + OIDC | ECR push・ECSデプロイの自動化 |
| 認証情報管理 | Secrets Manager | DB認証情報をコードにハードコードしない |

## 5. API一覧

### 認証

| メソッド | エンドポイント | 概要 | 認証要否 |
|----------|--------------|------|---------|
| POST | `/api/auth/register` | ユーザー登録 | 不要 |
| POST | `/api/auth/login` | ログイン | 不要 |
| POST | `/api/auth/logout` | ログアウト | 必要 |
| GET | `/api/auth/me` | ログインユーザー情報取得 | 不要（未ログイン時は401） |

### 客室

| メソッド | エンドポイント | 概要 | 認証要否 |
|----------|--------------|------|---------|
| GET | `/api/rooms` | 客室一覧取得（`?check_in=&check_out=`で空き絞り込み） | 不要 |
| GET | `/api/rooms/<id>` | 客室詳細取得 | 不要 |

### 予約

| メソッド | エンドポイント | 概要 | 認証要否 |
|----------|--------------|------|---------|
| GET | `/api/bookings` | 自分の予約一覧取得 | 必要 |
| POST | `/api/bookings` | 予約作成 | 必要 |
| POST | `/api/bookings/<id>/cancel` | 予約キャンセル | 必要 |

### ヘルスチェック

| メソッド | エンドポイント | 概要 |
|----------|--------------|------|
| GET | `/health` | ALBヘルスチェック用 |

## 6. エラーレスポンス仕様

すべてのAPIエラーは以下のJSON形式で返却する。

```json
{"error": "エラーメッセージ"}
```

| HTTPステータス | 意味 | 例 |
|--------------|------|-----|
| 400 | リクエスト不正 | 必須項目未入力、日付不正 |
| 401 | 未認証 | ログインが必要なエンドポイントに未ログインでアクセス |
| 403 | 権限なし | 他ユーザーの予約をキャンセルしようとした |
| 404 | リソースが存在しない | 存在しない客室ID・予約IDを指定 |
| 400 | 業務エラー | 二重予約・チェックアウト日がチェックイン日以前 |

## 7. データベース設計

### テーブル一覧

| テーブル名 | 概要 |
|-----------|------|
| users | ユーザー情報（認証・予約との紐付け） |
| rooms | 客室マスタ |
| bookings | 予約情報 |

### users テーブル

| カラム名 | 型 | 概要 |
|---------|-----|------|
| id | INT | 主キー |
| username | VARCHAR(80) | ユーザー名（一意） |
| email | VARCHAR(120) | メールアドレス（一意） |
| password_hash | VARCHAR(256) | ハッシュ化パスワード |

### rooms テーブル

| カラム名 | 型 | 概要 |
|---------|-----|------|
| id | INT | 主キー |
| room_number | VARCHAR(10) | 部屋番号（一意） |
| room_type | VARCHAR(50) | 部屋タイプ（シングル・ダブル・スイート） |
| price_per_night | DECIMAL(10,2) | 1泊料金（円） |
| capacity | INT | 定員 |
| description | TEXT | 説明文 |
| image_url | VARCHAR(255) | 客室画像URL |

### bookings テーブル

| カラム名 | 型 | 概要 |
|---------|-----|------|
| id | INT | 主キー |
| user_id | INT | ユーザーID（外部キー） |
| room_id | INT | 客室ID（外部キー） |
| check_in_date | DATE | チェックイン日 |
| check_out_date | DATE | チェックアウト日 |
| total_price | DECIMAL(10,2) | 合計金額 |
| status | VARCHAR(20) | 予約ステータス（confirmed / cancelled） |
| created_at | DATETIME | 予約作成日時 |

## 8. 制約・前提条件

- 決済機能は実装しない（本番運用を目的としないため）
- 管理者機能は将来対応（現フェーズはスコープ外）
- production環境の構築は将来フェーズ（現在はnonprod側の環境整備を先行して進めている）
- 独自ドメイン・ACM証明書の取得は検討中・後回し（技術的な必要性は薄く、他設計への影響もないためいつでも後付け可能）
- SECRET_KEYはSecrets Managerで管理し、ECSタスク起動時に自動取得する
