# 要件定義書

## 1. プロジェクト概要

| 項目 | 内容 |
|------|------|
| プロジェクト名 | Tomario（ホテル予約システム） |
| 目的 | ホテルの客室予約をオンラインで受け付け、空き状況の確認から予約完了までをWebで完結させる |
| 開発目的 | AWSインフラエンジニアへの転職を目的としたポートフォリオ。インフラ構成の再現性・運用性の証明を主目的とする |

システム構成・使用技術とその選定理由は[基本設計書](../basic-design/basic-design-high-level-spec.md)に記載する（本書は「何を満たすべきか」を扱い、実装手段は基本設計書・環境定義書に分離している）。

---

## 2. スコープ

### 対象ユーザー

一般ユーザー（ホテルの宿泊予約をしたい人）のみを対象とする。管理者ユーザーは対象外（4章参照）。

### In Scope

- 会員登録・ログイン・ログアウト
- 客室の空室検索・詳細閲覧
- 予約の作成・自分の予約一覧確認・キャンセル

### Out of Scope

- 決済機能（本番運用を目的としないため実装しない）
- 管理者機能（予約一覧確認・客室登録）
- 会員ランク・ポイント制度
- 予約内容の変更（キャンセル＋再予約のみ対応）
- 複数施設（チェーン）管理
- 独自ドメイン・ACM証明書（導入しない。判断の根拠は[ADR](../../tomario-steering/adr/infra/frontend/001-no-custom-domain.md)参照）

---

## 3. ユーザーストーリー

- 未登録ユーザーとして、会員登録をしてサービスを使い始めたい
- 登録済みユーザーとして、ログインして自分のアカウントを使いたい
- ユーザーとして、日程を指定して空いている客室を検索したい
- ユーザーとして、予約する前に客室の詳細（タイプ・定員・料金・説明・写真）を確認したい
- ログイン済みユーザーとして、客室を予約したい
- ログイン済みユーザーとして、自分の予約一覧を確認したい
- ログイン済みユーザーとして、不要になった予約をキャンセルしたい（ただし直前のキャンセルには手数料がかかることを理解した上で）

---

## 4. 機能要件

### 4.1 認証

- 未登録ユーザーは、ユーザー名・メールアドレス・パスワードを入力して会員登録できる
  - メールアドレス・ユーザー名はそれぞれ一意とする（重複時はエラー）
  - いずれかの項目が未入力の場合はエラーとする
- 登録済みユーザーは、メールアドレスとパスワードでログインできる（一致しない場合はエラー）
- ログイン済みユーザーはログアウトできる
- ログイン状態の永続化（「ログインしたままにする」等）は要件としない

### 4.2 客室検索

- ユーザーは、ログインなしで客室一覧を閲覧できる
- ユーザーは、チェックイン日・チェックアウト日を指定して、その期間に空いている客室だけに絞り込める
- ユーザーは、客室の詳細（部屋番号・タイプ・定員・料金・説明・画像）を確認できる

### 4.3 予約・キャンセル

- ログイン済みユーザーは、客室と宿泊期間を指定して予約できる
  - チェックアウト日はチェックイン日より後の日付に限る（同日・過去日はエラー）
  - 同一客室・同一期間に重複する予約（ステータスが`confirmed`のもの）は作成できない
  - 予約金額は「宿泊日数 × 1泊料金」で算出する
- ログイン済みユーザーは、自分の予約一覧を確認できる
  - 他ユーザーの予約は一覧に含まれない
- ログイン済みユーザーは、自分の予約をキャンセルできる
  - 自分以外の予約はキャンセルできない
  - チェックイン日当日・それ以降はキャンセルできない
  - キャンセル料は、チェックインまでの日数に応じて以下の通り算出する

    | チェックインまでの日数 | キャンセル料率 |
    |---|---|
    | 3日以上前 | 0%（無料） |
    | 2日前 | 30% |
    | 前日 | 50% |

    キャンセル料 = 予約金額 × 上記料率（端数は四捨五入）

### 4.4 エラーケース

- 未認証のユーザーが認証必須のエンドポイントにアクセスした場合 → 401
- 自分以外の予約をキャンセルしようとした場合 → 403
- 存在しない客室ID・予約IDを指定した場合 → 404
- 必須項目の未入力・日付の前後関係不正・二重予約など、業務ルールに反するリクエスト → 400

すべてのAPIエラーは`{"error": "エラーメッセージ"}`形式のJSONで返却する。

## 6. API一覧

### 認証

| メソッド | エンドポイント | 概要 | 認証要否 |
|----------|--------------|------|---------|
| POST | `/api/auth/register` | ユーザー登録 | 不要 |
| POST | `/api/auth/login` | ログイン | 不要 |
| POST | `/api/auth/logout` | ログアウト | 必要 |
| GET | `/api/auth/me` | ログインユーザー情報取得 | 不要（未ログイン時は401） |

### 客室

| メソッド | エンドポイント | 概要 | 認証要否 |
|----------|--------------|------|---------|
| GET | `/api/rooms` | 客室一覧取得（`?check_in=&check_out=`で空き絞り込み） | 不要 |
| GET | `/api/rooms/<id>` | 客室詳細取得 | 不要 |

### 予約

| メソッド | エンドポイント | 概要 | 認証要否 |
|----------|--------------|------|---------|
| GET | `/api/bookings` | 自分の予約一覧取得 | 必要 |
| POST | `/api/bookings` | 予約作成 | 必要 |
| POST | `/api/bookings/<id>/cancel` | 予約キャンセル | 必要 |

### ヘルスチェック

| メソッド | エンドポイント | 概要 |
|----------|--------------|------|
| GET | `/health` | ALBヘルスチェック用 |

## 7. データベース設計

### テーブル一覧

| テーブル名 | 概要 |
|-----------|------|
| users | ユーザー情報（認証・予約との紐付け） |
| rooms | 客室マスタ |
| bookings | 予約情報 |

### users テーブル

| カラム名 | 型 | 概要 |
|---------|-----|------|
| id | INT | 主キー |
| username | VARCHAR(80) | ユーザー名（一意） |
| email | VARCHAR(120) | メールアドレス（一意） |
| password_hash | VARCHAR(256) | ハッシュ化パスワード |

### rooms テーブル

| カラム名 | 型 | 概要 |
|---------|-----|------|
| id | INT | 主キー |
| room_number | VARCHAR(10) | 部屋番号（一意） |
| room_type | VARCHAR(50) | 部屋タイプ（シングル・ダブル・スイート） |
| price_per_night | DECIMAL(10,2) | 1泊料金（円） |
| capacity | INT | 定員 |
| description | TEXT | 説明文 |
| image_url | VARCHAR(255) | 客室画像URL |

### bookings テーブル

| カラム名 | 型 | 概要 |
|---------|-----|------|
| id | INT | 主キー |
| user_id | INT | ユーザーID（外部キー） |
| room_id | INT | 客室ID（外部キー） |
| check_in_date | DATE | チェックイン日 |
| check_out_date | DATE | チェックアウト日 |
| total_price | DECIMAL(10,2) | 合計金額 |
| status | VARCHAR(20) | 予約ステータス（confirmed / cancelled） |
| created_at | DATETIME | 予約作成日時 |

## 8. 将来拡張（バックログ）

現フェーズでは意図的に見送り、条件を満たしたときに実装する項目。いま実施すると決めた残作業は`tomario-workspace/task-and-flow/remaining-task.md`で管理する。

| 項目 | 今やらない理由 | 実装するきっかけ | 想定する対応 |
|------|--------------|----------------|------------|
| 管理者機能（予約一覧の確認・客室登録） | 一般ユーザー向けの予約導線の提供が現フェーズの目的のため | 運営者が画面から客室登録・予約確認を行う必要が出たとき | 管理者ロールと管理画面・APIを追加し、客室マスタのシード投入を置き換える |
| WAFのCOUNT/BLOCKモード切替え | 実ユーザーがいないため、BLOCKモードでの誤検知に実害が無い | 一般公開後に、新しいWAFルールを追加するとき | `override_action`を変数化し、COUNTで誤検知を確認してからBLOCKへ切り替える |
| request-idの付与・構造化ログ | スタックトレースの分断は`awslogs-multiline-pattern`で解消済みで、個別リクエスト単位の追跡が必要な場面が無い | 一般公開後など、個別リクエスト単位で障害を調査する必要が出たとき | `before_request`でrequest-id（`X-Amzn-Trace-Id`を流用、無ければ生成）を付与し、request-id付きの構造化ログを出力する |
| CloudWatch EMFによるカスタムメトリクス（予約件数・レスポンスタイム） | 業務指標を監視する要件が無い（インフラ指標で監視は足りている） | 予約件数などの業務指標を監視・可視化する必要が出たとき | `tomario-app`でEMF形式のログを出力し、ダッシュボード・アラームを追加する |
| productionでのPITRリストア訓練 | 破壊的操作のため、同一構成のstagingで訓練して代替している（実測RTO約14分） | 可用性の要件が上がったとき（Multi-AZの再検討と同時） | productionでPITRを実施し、RTOを実測する |

設計判断として見送り、ADRに再検討の条件を記載しているもの：RDS Multi-AZ（[ADR](../../tomario-steering/adr/infra/database/003-multi-az-cost-tradeoff.md)）、Blue/Greenデプロイ（[ADR](../../tomario-steering/adr/infra/backend/002-deployment-safety-net.md)）、独自ドメイン・ACM証明書（[ADR](../../tomario-steering/adr/infra/frontend/001-no-custom-domain.md)）、Performance Insights（[ADR](../../tomario-steering/adr/infra/database/004-performance-insights-instance-class-limitation.md)）

初期データ（客室マスタのシード投入）の仕様は、管理者機能が未実装であることに伴う運用上の暫定措置であり、運用設計（[backend-environment-design.md](../environment-definitions/backend-environment-design.md)）側で扱う。

## 9. 前提条件

- 決済機能は実装しない（本番運用を目的としないため）
- 管理者機能は将来対応（現フェーズはスコープ外）
- パスワードの複雑度要件は設けない（非公開のポートフォリオ用途のため）
- SECRET_KEYはSecrets Managerで管理し、ソースコードに含めない
